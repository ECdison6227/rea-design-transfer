# 选择风格与改造自己的软件

## 输入与范围

读取用户指定研究库的README、profile/library索引、覆盖、对照和迁移指南，然后审查目标软件源码及平台。目标是让新业务采用同一套产品设计语言，不默认移植原App的功能、业务数据或后端。

用户只让选型时输出有依据的比较与适配代价；用户让修改软件时推进实现。缺少目标项目位置则先完成来源库评估，再问必要输入，不擅自选择旁边无关仓库。

## 规则映射

用简表记录“来源规则→目标中的位置→保留/替换/适配→证据级别→验证方式”。关注：

1. **视觉家族感**：密度与留白、背景层级、字形角色、组件尺度、形状、图标、内容宽度与信息层级；不能只换品牌色。
2. **操作习惯**：主要动作位置、导航与返回、选择/编辑、保存/取消、焦点、快捷键、触摸/鼠标差异。
3. **反馈与可靠性**：加载/成功/错误、重复提交、取消、重试、离线、状态保留；来源未验证的策略由目标需求决定并标D。
4. **用户指引**：首次使用、功能发现、空态下一步、权限解释、校验文案、帮助入口、熟练用户路径。

保留目标已有业务正确性与用户数据；不要为了风格一致移除必要功能。保留来源中有效的设计关系，而非照搬健康/聊天/支付等领域词与流程。

## 实施

优先接入现有设计系统、组件库和平台能力。只在不合适时引入新栈；不要将网页中的假窗口按钮放进原生用户流程。字体、图标与壳按可用资产/平台调整，替换的度量和状态行为要重新比较。

先建立tokens映射与基础组件，再接代表页面和行为。必要逻辑包括IME、焦点恢复、返回/取消、空态和错误恢复。不要先做漂亮主页，再把其他状态留成无法操作的装饰。

## 验证与报告

在目标相同内容与环境下比较改造前后；需要检查来源风格时对照库中A原图并保留来源条件。目标实现的测试不证明来源原算法；与来源不同但符合目标需求的策略明确列为D。

验收重点是：新业务仍可用，并在多页面、多状态、引导和操作习惯上形成一致家族感。只让一个静态截图相似不够。报告具体修改、验证、视觉与行为偏差、独立选择和回退方法；按需更新目标风格映射，而不改写研究库的A/B事实。
